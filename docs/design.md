# 航运智能账单助手：设计与 Harness 说明

## 验收 Harness

Harness 将输入、期望字段、操作类型与风险预期固化为可重复执行的案例。测试分为四层：

1. **解析层**：EML 正文、递归附件、PDF 文本、OCR 返回、XLS/XLSX、DOC/DOCX；
2. **抽取层**：单据号、提单号、交易方、费用、金额、币种、付款方式；
3. **业务层**：费用标准化、AR/AP、CREATE/UPDATE/NO_CHANGE、重复与冲突；
4. **回归层**：每次修复均保存失败输入和期望 JSON，禁止因模型或规则变化使历史通过样例退化。

每一项输出必须同时断言：JSON Schema 合法、金额为数值、币种合法、每项费用独立成行、`audit_trail` 可定位证据。OCR 和 LLM 采用 mock 回归测试，并以真实服务的少量金标样例做独立集成测试。

## 设计思考

1. **将 LLM 限定为语义抽取器。** 金额计算、币种、账单匹配和更新范围由确定性规则兜底，避免模型直接入账。
2. **不确定时停下而非猜测。** OCR、字段校验、总额、重复或匹配出现风险时输出 `PENDING_REVIEW`，并留下原因。
3. **更新是补丁，不是覆盖。** 已匹配账单仅接受输入明确给出的变更，其余字段继承原账单，降低历史数据损坏风险。
4. **费用别名须配置化治理。** 原始费用与标准费用并存；映射表版本化维护，不把财务规则固化在提示词中。
5. **AR/AP 必须站在记账主体视角。** 结合当前记账主体、签发方/接收方和“应付/应收”费用方向；任一关键信息缺失时不强行判断。
6. **审计证据是一等数据。** 来源文件、原始文本、置信度、校验和匹配候选都进入 `audit_trail`，使财务可复核每个字段。
7. **测试要隔离外部不稳定性。** OCR 和 LLM 的单元测试使用 mock；真实 API 只做具备公网可访问测试文件的集成验证。
